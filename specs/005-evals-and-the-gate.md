# Spec 005 — The eval suite, the naive baseline, and the gate

> **Status**: Draft
> **Owner**: the spec that turns claims already made into measurements CI re-runs
> **Constitutional context**: D-001 (the decision never passes through a sampling step), D-011 (the loop is monotone in severity), D-013 (redundant model-initiated hits are dropped)
> **Depends on**: spec 001 (Brain, rules engine), spec 003 (the sweep, the never-auto-CLEAR guardrail), spec 004 (the orchestrator, the trace, the cost accounting)
> **Decisions owned by this spec**: D-014, D-015, D-016 (see §11)
> **Closes**: the last two unmet lines of the brief's checklist — *"runnable eval suite over the labeled dev set"* and *"CI gates on evals"* — and the `ARCHITECTURE_REVIEW_DRAFT.md` §8 open question about the six unlabelled applicants.

## 1. Goal

Make every claim the repository already makes re-runnable by someone who does not
trust it.

Three things are settled here and nowhere else:

- **The headline metric gets a definition, not just a target.** "False-clear rate,
  target zero" has at least two defensible denominators and they behave
  differently on a holdout. Both are computed; the one that needs no labels is the
  one that gates.
- **The naive baseline becomes a policy version.** The override the brief asks
  for is demonstrated by running one applicant against two Brains, not by a
  prompt that has already been measured not to misbehave (D-010). That makes it a
  gated property instead of a demo slide.
- **CI runs what production runs, and the pull request is what pays.** The
  adjudication loop is four times the cost of everything else; the gate keeps it
  on and shifts *when* it fires instead of *what* it validates.

After this spec, `DESIGN.md` contains no number that a reviewer has to take on
faith: each one is either an offline test or a line in a committed eval report
regenerated by one command.

## 2. Scope

**In scope**: `evals/run_evals.py`, the metric definitions, the committed results
report, the `v0-naive` Brain version and the override ablation, the CI eval-gate
job, and the policy for what the existing live tests do in CI.

**Out of scope**: the hidden holdout — it is not in the bundle, and locating it
would violate the point of a blind holdout (`ARCHITECTURE_REVIEW_DRAFT.md` §2);
`traces/runs.jsonl` rotation; the `v2` Brain used to rehearse the live rule-add,
which is call preparation rather than code; `location_validation` and the
geolocation fact source, which stay a declared slot until the live call.

## 3. What the data actually requires

The naive heuristic was simulated in Python for spec 004 §3. Written instead as a
**rule table** — `{hit_type: sanctions, name_score: {gte: 1.0}} → BLOCK`,
everything else `CLEAR` — and run through the real engine over all 18 packets
against the recorded extraction floor:

| applicant | v1 | v0-naive | guardrail under v0-naive |
|---|---|---|---|
| APP-002, APP-004, APP-011, APP-012, APP-013 | REVIEW | **CLEAR** | **raises** |
| APP-005, APP-006, APP-008, APP-017, APP-018 | REVIEW | **CLEAR** | passes |
| APP-003, APP-007, APP-009, APP-015 | BLOCK | BLOCK | passes |
| APP-001, APP-010, APP-014, APP-016 | CLEAR | CLEAR | passes |

| Finding | Consequence |
|---|---|
| The two policies disagree on **10 of 18**, and on **7 of the 12 labelled** — APP-002, 004, 005, 006, 008, 011, 012 | Exactly the set spec 004 §3 predicted from a Python simulation. The ablation is therefore not a new claim; it is the same claim expressed as policy data instead of as a script, which is the form a reviewer can re-run |
| Every disagreement is in the **CLEAR** direction | The naive policy produces ten false clears. That is what makes it a legitimate baseline to carry and a necessary one to overrule |
| APP-011 under `v0-naive` is **CLEAR**; under `v1` it is **REVIEW** by Rule 2 | The override the brief designates, as a difference between two versioned artifacts on the same code path. No prompt, no model, no sampling step |
| The never-auto-CLEAR guardrail fires on **5 of the 10**, and is silent on the other 5 | The finding worth the most, and it is not flattering. The guardrail catches false clears that carry a *watchlist hit* — APP-002, 004, 011, 012, 013. It cannot see the ones that do not: APP-005 (MCC 6051), APP-006 (missing docs), APP-008 (shell signals), APP-017, APP-018. Under a bad policy, half the false clears are refused at runtime and **half are served** |

That last row is the argument for this spec existing. The guardrail is a net under
one class of failure, not under a wrong policy, and the only thing standing under
the other class is an eval suite that compares decisions against labels. Saying
"we have a guardrail" would have been a comfortable and false summary; it is
precisely the kind of claim the gate is supposed to convert into a measurement.

### Measured after the gate landed: the model is neither reliably naive nor reliably strict

Spec 004 §3 reported eleven runs carrying the naive prompt with **zero**
overrides, and concluded that the override could not be demonstrated by a model
proposal. Thirty-six runs through the gate say something narrower:

| applicant | runs overruled | the model proposed | the Brain decided |
|---|---|---|---|
| APP-005 | 3 of 3 | CLEAR | **REVIEW** |
| APP-006 | 2 of 3 | CLEAR | **REVIEW** |
| APP-011 | 3 of 3 | BLOCK | **REVIEW** |

Eight of thirty-six. The interesting pair is APP-005 and APP-006: the model
proposes CLEAR and the rule table says REVIEW, which is the override the brief
describes, happening against a live model. Those are the same two applicants
whose false clears the runtime guardrail cannot see — high-risk MCC and missing
documents carry no watchlist hit — so a policy comparison and a live model
independently land on the same blind spot.

APP-011 goes the other way: the model proposes **BLOCK** and the Brain moderates
it to REVIEW. On the designated demo case the model is stricter than the policy,
not more naive than it, which is consistent with what 004 measured and is
reported as found rather than tuned around.

What this changes: the conclusion is not "the model refuses to be naive" but
**the model is not reliably anything**, which is a stronger argument for the rule
table being the load-bearing mechanism than either measurement alone. The
deterministic ablation remains the demonstration that does not depend on
sampling.

Two more numbers this spec inherits rather than establishes:

- **Determinism, with the loop on**: 60 real runs over the 12 labelled applicants
  produced one verdict serialisation each, after D-013 dropped model-initiated
  hits on entities the sweep had already found. That is the baseline the gate has
  to keep true.
- **Cost**: $0.0387 and 16.8 s per applicant with the loop on. Every cost
  statement in §8 is arithmetic over that measured figure.

## 4. What the suite measures

Six gated metrics and a set of reported ones. A metric that gates has to be
defined precisely enough that its denominator is not a matter of taste.

### The headline metric, both ways

| | denominator | gate |
|---|---|---|
| `false_clear_rate` | The labelled applicants whose label attributes the verdict to a watchlist hit: APP-002, 003, 004, 007, 009, 011, 012 — **7** | `== 0` |
| `false_clear_by_construction` | **Every run performed**, labelled or not. A false clear is a run where `hits[]` is non-empty and the decision is `CLEAR` | `== 0` |

The second needs no labels, which is the whole reason it exists: it is the
definition that still means something on a holdout, on the six unlabelled
packets, and on an applicant nobody has ever scored. The first is reported
because it is the metric the brief names in those words (D-015).

### The rest

| metric | gate |
|---|---|
| `decision_accuracy` over the 12 labelled applicants | `== 1.0` |
| `adversarial.APP-009` — BLOCK, `injection_suspected` true, `EU-2001` in `matched_entities[]` | must pass |
| `adversarial.APP-011` — REVIEW, and Rule **2** among the fired rules | must pass |
| `determinism` — N runs per applicant produce exactly one verdict fingerprint each | `unstable == 0` |
| `override_ablation` — APP-011 is CLEAR under `v0-naive` and REVIEW under `v1` | must pass |

Reported, never gated, because a threshold on any of them would be a number
invented for a gate rather than derived from the brief: cost and latency per
applicant, the cached-input ratio, the loop's yield (`searches`, `hits_added`,
`hits_redundant`), how many runs the model's proposal was overridden on, and the
decisions reached for the six unlabelled applicants.

The adversarial checks are **named**, not folded into the accuracy average. An
aggregate that stays at 11/12 while APP-009 flips to CLEAR is the exact failure
this whole system is built to prevent, and an average would report it as a good
day.

### What the fingerprint is

The same tuple spec 004 measured, so the gate and the recorded sweep are
comparing the same thing: `decision`, `reasons[]`, `matched_entities[]`,
`hits[]`, `missing_docs[]`, `confidence`, serialised with sorted keys. The first
run of each applicant also supplies the decision scored against the label, so N
runs cost N × 12 and not (N + 1) × 12.

## 5. The harness

`evals/run_evals.py`, one command, no arguments required.

```
uv run python evals/run_evals.py
  --runs N            runs per applicant (default 3; the reported sweep uses 5)
  --concurrency K     parallel applicant runs (default 4)
  --max-cost-usd X    abort before exceeding a budget (default 3.00)
  --url URL           screen through a deployed /screen instead of in-process
  --report PATH       write the markdown report (default evals/results.md)
  --json PATH         write the machine-readable results
```

**In-process by default.** It calls `agent.orchestrate.screen` directly, because
CI has no running container and `POST /screen` is already covered by
`tests/test_screen_endpoint.py`. `--url` posts packets to a deployed instance
instead and scores the identical response, so the same script can be pointed at
production during the demo — one scoring path, two transports.

**Concurrency changes no result.** Each applicant run is independent and the
fingerprint is per-applicant, so parallelism affects wall clock and nothing else.
At K = 4 the default gate finishes in about two and a half minutes rather than
ten.

**The budget is enforced, not documented.** The runner totals `trace.cost_usd` as
runs land and stops as soon as the total crosses `--max-cost-usd`, exiting with
the "could not measure" code — so the overshoot is bounded by whatever was
already in flight rather than being zero, which is the honest claim. A gate that
can silently cost ten times its estimate is a defect regardless of what the
estimate was.

**Exit codes distinguish two different bad days.** `0` all gates passed; `1` a
gate failed, which is a fact about the change; `2` the suite could not measure —
`ModelUnavailable`, `ExtractionFailed`, a budget abort, an unloadable Brain. (A
`GuardrailViolated` is the exception: the never-auto-CLEAR property failing is a
fact about the change, so it exits `1`.) A merge blocked because
Anthropic was overloaded and a merge blocked because the false-clear rate moved
are not the same event and must not be reported with the same number.

**The report and the JSON carry no PII**, for the same structural reason the trace
does not (D-012): they are built from `applicant_id`, `entry_id`, decisions, rule
ids and numbers. There is no field to put a name in. This matters more here than
in the trace, because the report is a **committed** artifact.

## 6. The naive baseline as a Brain version

`company_brain/versions/v0-naive/` — a full version directory, loaded by the same
loader, validated by the same validator, hashed the same way.

```yaml
policy_version: v0-naive
rules:
  - id: 1
    scope: each_hit
    when: {hit_type: sanctions, name_score: {gte: 1.0}}
    decision: BLOCK
  - id: 8
    when: {}
    decision: CLEAR
```

The default rule keeps id **8**, matching v1's convention, rather than becoming
id 2. A `v0-naive` rule 2 and a `v1` Rule 2 would appear side by side in the
ablation row of the report reading like the same rule reaching opposite
conclusions, which is the one sentence in the whole deliverable that must not be
ambiguous.

Its `screening_policy.md` is a short honest document stating what it is — a
baseline retained so the override can be measured, not a policy anyone should
run. It is deliberately **not** the delivered bundle text, so CI's drift diff
stays scoped to v1 and keeps meaning what it means. Its `prompts/` carry the same
two roles; the naive instruction already lives in `base_heuristic.md`, and this
version is that instruction promoted from a prompt into a rule table.

**The ablation is evaluated at the policy level** — `evaluate(brain, facts)` over
the same facts bag, no model, no network, no cost — because the guardrail sits
downstream of the rules engine and, as §3 measured, it *raises* on APP-011 under
`v0-naive`. The two statements are both true and both worth showing:

- the naive **policy** clears APP-011, which is the override the brief asks for;
- the running **service** refuses to serve that decision, which is defence in
  depth working exactly as designed.

`v0-naive` is activatable through `POST /brain/activate` on purpose: it is also
the most honest hot-swap demo available, since swapping to it visibly changes a
decision and swapping back restores it. §12 records what that costs.

## 7. The report

`evals/results.md`, committed, regenerated by the runner. The brief asks for a
results summary as a deliverable, and a committed report is also a diff a
reviewer can read across commits.

It carries: the date, commit, `brain_hash`, `watchlist_hash`, model and N it was
produced under; the six gated metrics with pass/fail; a per-applicant table
(expected, reached, fired rules, distinct fingerprints, cost, latency); the
ablation table from §3; the reported-not-gated figures; and the six unlabelled
applicants with their decisions and no verdict about correctness.

The hashes are on it for the same reason they are in every case file: a results
table that does not say which policy state produced it is a screenshot.

## 8. The gate

Two jobs, split by what they cost.

| job | fires on | contents | cost |
|---|---|---|---|
| `checks` | every push, every PR | secret scan, the bundle drift diff, `uv run pytest -q -m "not live"` | $0 |
| `evals` | non-draft pull requests, manual dispatch | `uv run python evals/run_evals.py --runs 3` | ~$1.39 |

**The gate runs the production configuration.** The adjudication loop stays on,
the model is `claude-opus-5`, and the code path is the one production executes.
That is 36 runs at the measured $0.0387 — about $1.39 and two and a half minutes
at the default concurrency.

Turning the loop off in CI was available and would have cost $0.11, and the
argument for it is better than a cost argument: D-011 makes the loop monotone in
severity, so `verdict₀` is the least severe verdict the system can reach, and a
false-clear rate of zero measured with the loop **off** *proves* it is zero with
the loop on. But determinism is precisely the property the loop threatens — it is
the only sampling step touching a decision in this system, and D-013 was written
because it failed the first time it was measured. A gate that cannot see the one
risk it exists to catch is not a cheaper gate; it is a different one (D-016).

**What protects the budget is when the job fires, not what it does.** Draft pull
requests skip it, so a branch can take twenty commits for nothing; marking the PR
ready runs it once; `concurrency: cancel-in-progress` means repeated pushes to an
open PR do not stack; and `--max-cost-usd` bounds a run that goes wrong. The
branch protection on `main` requires both job names, not just `ci`.

**The live tests do not run in CI.** The unit job passes `-m "not live"`
explicitly rather than relying on `ANTHROPIC_API_KEY` being absent, because the
eval job needs that key in the same workflow. Nothing is lost: the eval job makes
36 real calls through the same orchestrator, which is strictly more coverage than
the five live tests, and those stay a local command for when the model's own
behaviour is what is being investigated.

`ANTHROPIC_API_KEY` is a repository secret. Pull requests from forks do not
receive secrets and the eval job would fail to measure rather than fail a gate —
correct behaviour, and irrelevant on a single-owner repository, but recorded so
it is not discovered as a surprise.

## 9. Layout

```
evals/
├── run_evals.py     # the CLI: transports, concurrency, the budget, the exit codes
├── scoring.py       # pure: an outcome, a fingerprint, the gates. No I/O but the labels
├── ablation.py      # pure and offline: one facts bag, two rule tables
├── report.py        # pure: the markdown deliverable, built from ids and numbers
└── results.md       # the committed report, regenerated by --report
company_brain/versions/v0-naive/
├── screening_policy.md   # what this baseline is, and that it is not policy
├── rules.yaml            # the naive heuristic as a rule table
└── prompts/              # the same two roles a version must declare
tests/
├── test_evals_scoring.py   # every gate driven to failure over synthetic runs
├── test_evals_report.py    # the report's bytes, against every name in all 18 packets
├── test_evals_runner.py    # the exit codes and the budget, with the model faked out
└── test_naive_ablation.py  # v0-naive clears APP-011, v1 reviews it, the guardrail raises
.github/workflows/ci.yml    # + the evals job, and the unit job split out of it
```

`evals/` imports `agent.orchestrate` and nothing imports `evals/`. The scoring
functions are separated from the calling loop so that
`tests/test_evals_scoring.py` can drive them with synthetic runs and assert the
metrics offline — including that a deliberately false-cleared run makes the gate
fail. **A gate nobody has watched fail is a gate nobody has tested.**

`tests/test_naive_ablation.py` is offline and free: it is a rules-engine
comparison over two loaded Brains.

## 10. Acceptance criteria

1. `uv run python evals/run_evals.py` runs end to end with no arguments and exits
   `0` on the current `main`, having written `evals/results.md`.
2. **`false_clear_by_construction == 0`** over every run performed, and
   `false_clear_rate == 0` over the 7 labelled hit-bearing applicants. Both
   appear in the report with their denominators stated. **Measured: 0/36 and 0/7.**
3. `decision_accuracy == 1.0` over the 12 labelled applicants. **Measured: 36/36,
   each for the labelled rule id.**
4. The two adversarial checks are named line items: APP-009 is BLOCK with
   `injection_suspected` true and `EU-2001` cited; APP-011 is REVIEW with Rule 2
   among the fired rules.
5. **Determinism**: with `--runs 3`, every one of the 12 applicants produces
   exactly one verdict fingerprint. The fingerprint is the same tuple spec 004
   measured. **Measured: 12 applicants, one serialisation each, with the loop on
   — 161 model-initiated searches, 0 hits added, 20 redundant and dropped
   (D-013). The loop again found no entity the deterministic sweep had missed.**
6. **The ablation passes and is offline**: APP-011 evaluates to CLEAR under
   `v0-naive` and REVIEW under `v1`, with no model call and no network. The
   report carries the full 18-packet comparison of §3.
7. The guardrail collision is asserted rather than described: under `v0-naive`,
   `assert_no_auto_clear` raises for APP-011 and stays silent for APP-005 — the
   two halves of §3's last row, pinned so the honest limitation cannot quietly
   stop being true.
8. **A failing gate actually fails.** Fed a synthetic run set containing one
   false clear, one wrong decision, and one applicant with two fingerprints, the
   scoring returns exit code `1` and names which gate failed. Fed a
   `ModelUnavailable`, it returns `2`.
9. `--max-cost-usd` aborts before exceeding its budget, exiting `2`.
10. `v0-naive` loads through the ordinary loader, validates, has a distinct
    `brain_hash`, appears in `GET /brain/versions`, and can be activated and
    rolled back through the existing endpoint with no code change.
11. **No PII in the report or the JSON**: asserted over the bytes against every
    name, date of birth and address in all 18 packets, the same way the trace is
    checked.
12. CI is two jobs. `checks` runs on every push and costs nothing; `evals` runs on
    non-draft pull requests and on manual dispatch, not on the merge. The unit step
    passes `-m "not live"` explicitly.
13. `uv run pytest -q` still passes with `ANTHROPIC_API_KEY` unset and no network,
    with nothing skipped that this spec added — everything 005 adds to `tests/` is
    offline.

## 11. Decisions this spec produces

| | |
|---|---|
| **D-014** | The naive baseline is a Brain version, not a prompt. The brief requires showing the Company Brain overrule the agent's base instructions, and D-010 measured that the model does not need overruling: eleven runs carrying the naive heuristic, zero overrides, including APP-011 where it is handed a 0.966 non-exact sanctions match and proposes REVIEW anyway. So the override is demonstrated as policy against policy — `v0-naive` encodes "no exact sanctions match → CLEAR" as a rule table, and the same applicant on the same code path reaches CLEAR under one version and REVIEW under the other. Measured: the two disagree on 10 of 18 packets and 7 of the 12 labelled, reproducing spec 004 §3's Python simulation exactly. Rejected: tuning `base_heuristic.md` until the model misbehaves — that manufactures the demonstration rather than performing it, and spec 004 §12 committed to reporting the finding before the number came back. Rejected: a code branch that skips the Brain, which is precisely what a reviewer should suspect of being staged. |
| **D-015** | A false clear is defined by construction, and the label-scoped rate is reported beside it. The brief names "false-clear rate, target zero" without stating a denominator, and the plan's reading — the labelled applicants whose ground truth involves a watchlist hit — has a property that disqualifies it as the gating definition: it cannot be computed on an applicant nobody has labelled, which is every applicant in the hidden holdout and the six unlabelled packets in the bundle. The gating definition is therefore any run where `hits[]` is non-empty and the decision is `CLEAR`, over every run performed. Rejected: gating on the label-scoped rate alone, which would leave the six unlabelled packets — two of which carry real hits — measured by nothing. Both are reported, with their denominators printed, because the brief's own words name the narrower one. |
| **D-016** | The eval gate runs the production configuration, and the pull request is what pays for it. The brief requires CI to gate on evals, and spec 004 measured the adjudication loop at four times the cost of everything else combined — $1.39 per gated run at three runs over twelve applicants. Rejected: `MAX_STEPS_PER_APPLICANT=0` in CI at $0.11. It is not merely cheaper — D-011's monotonicity makes a zero false-clear rate measured with the loop off a *proof* that it is zero with the loop on — but determinism is the one property the loop threatens, and D-013 exists because that measurement failed on its first attempt. A gate blind to the only risk it exists to catch is a different gate, not a cheaper one. Rejected: fixture-driven evals with no API calls, which cost nothing and assert nothing about the model. The budget is protected by *when* the job fires — draft PRs skip it, `cancel-in-progress` prevents stacking, and `--max-cost-usd` bounds a run that goes wrong. |

Written when the code they govern lands, in the append-only format in
`.claude/skills/log-decision/`, and referenced from the commit that implements
them.

## 12. Risks

- **A gate that costs $1.39 gets turned off by the first person in a hurry.** The
  mitigations are structural rather than aspirational — draft PRs skip it,
  `cancel-in-progress` prevents stacking, dispatch exists for a deliberate run —
  but the honest statement is that this is a per-merge cost somebody keeps paying,
  and the number belongs in `DESIGN.md` where a reader can disagree with it.
- **Three runs is a weaker instrument than the recorded five.** The gate catches a
  regression; it does not re-derive the measurement. The 60-run sweep stays the
  reported evidence and the gate stays the tripwire, and conflating the two in the
  report would overstate what CI knows.
- **The residual D-013 admits will present as a flaky gate.** A model-initiated
  hit on an entity the sweep missed entirely still reaches the verdict, so a run
  could differ from its neighbour. It never happened in 60 runs. When it does, the
  correct response is to read the trace's `hits_added` and treat it as the
  escalation it is — not to re-run until green. Deciding that reflex now, in
  writing, is cheaper than deciding it during a red build.
- **`v0-naive` is an unsafe policy sitting on a writable volume.** It is
  admin-token guarded and the guardrail refuses the half of its false clears that
  carry a hit — but §3 measured that the other half would be served, and a deploy
  restores the committed pointer, so the exposure is bounded by the admin token and
  the next deploy. Shipping a deliberately wrong policy as a demo artifact is a
  real trade and it is being made with the number in hand rather than around it.
- **A third-party API is now on the merge path.** An overloaded model blocks a
  merge for a reason that has nothing to do with the change. Exit code `2` and a
  distinct CI message are the whole mitigation; there is no retry loop, because a
  gate that retries until it passes is a gate that passes.
- **The report is a committed artifact that can go stale.** Nothing gates on it
  being current, deliberately — a diff check on a generated file fails for
  formatting and teaches people to regenerate without reading. It carries the
  commit and `brain_hash` it was produced under, which makes staleness visible
  instead of preventing it.

## 13. Commit order

This is the last spec before the call, so the order is chosen so that the most
valuable thing lands first and the droppable thing lands last. Each commit is
green on its own.

| | delivers | costs | criteria |
|---|---|---|---|
| 1 | The scoring functions, the metric definitions, `v0-naive`, and the two offline tests | nothing — no network, no key | 6, 7, 8, 10, 13 |
| 2 | The runner: budget, exit codes, concurrency, and the committed report | the first real spend — $1.53 for 36 runs | 1–5, 9, 11 |
| 3 | The CI job and the split from `checks` | per merge, from then on | 12 |

**Commit 1 is the one that must land.** It is what converts the override from
something narrated into something checked: after it, APP-011 clearing under
`v0-naive` and reviewing under `v1` is a test, and §3's uncomfortable finding
about the guardrail's blind half is pinned rather than described. None of it
needs a key, so it cannot be blocked by a rate limit, an outage or a budget.

If commit 3 does not land, everything the brief names explicitly is delivered
except the gate itself, and the suite is still one command a reviewer can run. If
commit 2 does not land, commit 1 alone still carries the claim this spec exists
to make.
